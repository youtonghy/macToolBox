# DDPM 显示器控制文档待确认问题清单

日期：2026-07-30

## 1. 目的

本清单用于向 DDPM 文档提供方集中确认目前仍存在歧义、相互矛盾或缺少实机证据的内容。

这些问题会直接影响 macToolBox 在保留现有 DDC 控制能力的基础上，新增以下功能时的安全性和兼容性：

- 亮度、对比度及相关 DDC 状态刷新；
- 色彩预设、色域模式和 RGB Gain；
- 显示器硬件预设与 macOS ICC Profile 联动；
- HDR、定时色域和按应用切换；
- Intel、Apple Silicon 和 USB 三类传输路径的一致行为。

希望提供方在回复问题的同时，输出一份已经合并修正的新版文档，而不只是继续追加勘误。新版文档应确保协议、API、示例代码和实现建议之间只有一个权威结论。

## 2. 建议的答复格式

请针对每个问题至少提供以下信息：

1. **明确结论**：实现方最终应该遵循的唯一规则。
2. **适用范围**：Mac 架构、macOS 版本、连接方式、显示器型号和固件版本。
3. **原始证据**：实机 DDC 报文、日志、反编译调用链、SDK 定义或可运行示例。
4. **失败语义**：如何区分不支持、暂时失败、只写能力和协议错误。
5. **降级方案**：无法读取能力或验证结果时，产品应该如何处理。

建议在新版文档中给每项结论标注证据等级：

- `[已验证]`：有实机测试或完整调用证据；
- `[逆向推断]`：来自反编译，但尚未完成实机验证；
- `[实现建议]`：提供方建议的设计，不代表 DDPM 当前真实行为；
- `[待实测]`：目前仍不能作为实现依据。

## 3. P0：开始实现色彩功能前必须明确

### Q1. Capability String 到底使用哪个 VCP 命令？

当前文档存在直接冲突：

- `03-ddci-protocol.md` 和 `06-api-reference.md` 使用 `0xF00`；
- `08-implementation-prerequisites.md` 和 `09-errata-and-corrections.md` 使用分段读取命令 `0xF3`。

请明确：

1. Intel DDC、Apple Silicon IOAVService 和 USB SDK 分别使用哪个命令？
2. `0xF00` 是笔误、内部 API 编号，还是另一种协议路径？
3. `0xF3` 的完整请求与响应格式是什么？
4. 分段偏移量、块头、有效负载长度、结束条件和最大长度如何定义？
5. 每段的 checksum 如何计算？
6. 每段之间需要多长延迟，失败后如何重试？

需要提供：

- 至少一组完整 Capability String 的原始请求和响应报文；
- Intel、Apple Silicon、USB 三条路径各自的实际调用证据；
- 一份可直接实现的分段读取伪代码或参考代码。

### Q2. Get VCP Feature 响应究竟是 11 字节还是 12 字节？

当前文档对返回长度和字段位置存在冲突：

- 一处定义 12 字节响应，最大值位于 `[6...7]`，当前值位于 `[8...9]`；
- 另一处定义 11 字节响应，并给出了不同的状态、类型、最大值和当前值偏移。

请分别明确 Intel、Apple Silicon 和 USB 路径的：

1. 完整响应字节布局；
2. 响应长度；
3. result/status、VCP code echo、VCP type、maximum value、current value 的位置；
4. checksum 字节的位置和校验范围；
5. 不支持、checksum 错误、总线错误和只写功能的实际响应。

需要提供以下原始样本：

- 正常读取成功；
- 显示器明确返回“不支持”；
- 传输超时或瞬时失败；
- checksum 错误；
- 写入支持但读取不支持。

### Q3. 读取失败的结果语义如何区分？

实现必须能够区分以下状态：

- 成功读取；
- 显示器明确不支持该 VCP；
- 瞬时通信失败，可以重试；
- 功能支持写入，但不支持读取；
- 响应格式或 checksum 无效。

请明确：

1. 每种状态对应的底层返回值、状态码或响应特征是什么？
2. 哪些错误允许重试，建议重试多少次？
3. 哪些错误可以缓存为“不支持”，缓存多久？
4. DDPM 是通过 Capability String 判断支持情况，还是会逐个读取探测？
5. Apple Silicon IOAVService 是否有已验证的状态码映射？

对于色彩预设等枚举型 VCP，如果无法判断支持状态，是否要求默认关闭 UI，而不是尝试写入？

### Q4. 无法读取 Capability String 时，允许采用什么降级策略？

当前文档同时出现了两种相互冲突的建议：

- 无法确认枚举值时，视为不支持并禁用；
- 使用全局值表尝试写入，然后通过读回验证。

请提供唯一、明确的安全策略：

1. 无法读取 Capability String 时，是否允许写入 `0x14`？
2. 是否仅允许对已验证型号和固件使用 allowlist？
3. 是否允许存在显式的“实验性控制”入口？
4. 如果显示器支持写入但不能读回，应该如何判断成功？
5. 失败写入是否可能改变显示器状态或造成黑屏、模式锁定等风险？

### Q5. VCP `0x14` 的数值含义是标准定义还是厂商映射？

当前文档将多个值直接解释为：

- `0x0B`：sRGB；
- `0x07`：Adobe RGB；
- `0xA1`：Display P3；
- 以及其他色域或预设模式。

请明确：

1. 这些值是 MCCS 标准定义、Dell 全系列统一定义，还是特定型号/固件映射？
2. Capability String 只表示允许值，还是也能确定每个值的人类可读名称？
3. DDPM 如何把 `0x14` 的数值映射为 “sRGB”“P3”“Adobe RGB”等名称？
4. 映射是否来自显示器型号表、固件表、显示器资产文件或远端配置？
5. 同一个值在不同厂商或不同 Dell 型号中是否可能表示不同模式？
6. 对未知厂商、未知型号或未知值应该显示原始值、隐藏选项，还是完全禁用控制？

需要提供一份包含显示器型号、固件版本、`0x14` 值及显示名称来源的真实映射样例。

### Q6. Capability String 的完整语法和解析规则是什么？

请明确解析以下结构时的规范：

1. `vcp(14(...))` 中嵌套允许值的语法；
2. 十六进制值是否可能带 `0x`、小写字母或不同位数；
3. 空格、换行、重复 section 和多个 `vcp(...)` 的处理；
4. 嵌套括号最大深度；
5. 数据被截断、括号不完整或出现厂商扩展时的处理；
6. `14` 存在但没有嵌套值时，代表“不支持枚举读取”“所有值未知”还是其他含义；
7. Capability String 是否可能在切换预设、HDR、PIP/PBP 或输入源后发生变化。

请提供：

- 多个真实显示器的完整 Capability String；
- 每个字符串对应的预期解析结果；
- 至少一组畸形或分段不完整数据的处理结果。

## 7. 新版文档验收标准

提供方给出的新版文档应满足：

1. 原章节已经直接修正，不再要求读者同时合并正文和多份勘误。
2. Capability String 命令、Get VCP 字节布局和 checksum 只有一套权威定义。
3. Intel、Apple Silicon、USB 三类后端分别说明，不能默认行为相同。
4. 每个 `0x14` 名称映射都注明标准来源或型号/固件适用范围。
5. 明确定义“不支持”“暂时失败”“只写”和“响应无效”。
6. 写后验证、重试、刷新和失败状态有统一状态机。
7. HDR 描述区分“检测”“阻止不兼容切换”和“实际切换系统 HDR”。
8. ICC 使用当前可用 API，并给出身份映射、应用确认和权限测试结果。
9. 双向同步、定时切换和远程更新若未实证，应明确标记为待实现或待验证。
10. 所有示例报文通过自动化 checksum 测试，所有伪代码中的变量、返回值和状态转换完整可执行。
